ABSTRACT

This project presents Institution ERP, a Student Information System and institution management platform built on Frappe v16 for Bannari Amman Institute of Technology. Institutional administration today depends on fragmented, manual processes that create data silos and increase the compliance burden. The aim of this work was to design and implement a unified system covering the full student lifecycle — from admissions inquiry through graduation — across academics, attendance, examinations, fees, library, hostel, transport, and institutional communication. The methodology adopts a hybrid architecture: a Vue 3 portal for students and guardians, role-specific Vue cockpits for staff, and a rebranded Frappe Desk for full CRUD operations. Row-level security is enforced through User Permissions and permission_query_conditions, with results publication gating controlling mark visibility. The implemented system comprises 48 DocTypes across 10 modules, 8 custom roles, 11 whitelisted API methods, and 16 row-level permission conditions, deployed at zero infrastructure cost on an open-source stack. Results demonstrate secure role-scoped access, automated student and guardian creation on admission approval, automatic grade calculation, fee recomputation, and library fine handling.

Keywords: Institution ERP, Student Information System, Frappe v16, Role-Based Access Control, permission_query_conditions, Vue 3.

ABBREVIATIONS AND NOMENCLATURE

CHAPTER I

INTRODUCTION

Higher education administration in India depends heavily on manual, paper-based, and fragmented digital systems. Admissions, academics, attendance, examinations, fees, library, hostel, transport, and institutional communication are often maintained through separate spreadsheets, registers, and standalone applications that do not share data. This fragmentation creates data silos, duplicates effort, slows decision-making, and increases the compliance burden on institutions. There is a clear need for an integrated Enterprise Resource Planning (ERP) system that unifies the entire student lifecycle — from first enquiry through graduation — within a single, secure, role-scoped platform.

Bannari Amman Institute of Technology (BIT), the demo brand for this project, administers multiple programs, courses, student groups, instructors, and thousands of academic and financial records each year. Managing these records across disconnected systems leads to inconsistent student data, difficulty in producing consolidated reports, and limited visibility for students and guardians into attendance, results, and fees. Existing institutional software is often either too generic to reflect Indian academic workflows (entrance tests, fee structures, results publication gating) or too expensive and rigid to deploy at scale. A purpose-built Student Information System (SIS) on an open-source, extensible platform addresses these gaps.

In the Indian higher-education context, the problem is compounded by regulatory and accreditation requirements. Institutions must submit data to statutory bodies, maintain attendance percentages for university compliance, track fee collections for financial audits, and produce examination result sheets for degree certification. Manual processes make these reporting obligations error-prone and time-consuming. Staff spend disproportionate effort on data entry and reconciliation rather than on student-facing academic work. A unified ERP reduces this administrative overhead, improves data accuracy, and gives leadership real-time visibility into institutional operations.

Furthermore, students and guardians currently have no self-service access to their records. A student must visit the office to check attendance, results, or fee dues. A guardian with multiple children must maintain separate logins or rely on the student to relay information. This lack of transparency erodes trust and increases administrative queries. A student and guardian portal with row-level scoping addresses this directly, giving each stakeholder secure, immediate access to their own data.

1.1 BACKGROUND

Educational institutions operate as complex organizations with interdependent functions. The admissions function manages inquiries, applications, entrance tests, and approvals. The academics function manages programs, courses, schedules, instructors, and student groups. The attendance function records student and staff presence. The examination function manages grading scales, assessment plans, marks entry, and result publication. The fees function manages fee structures, schedules, invoices, payments, and discounts. The library function manages books, memberships, issues, returns, and fines. The hostel function manages rooms and allocations. The transport function manages vehicles, routes, and student allocations. The communication function manages notices, feedback, and institutional dashboards.

When these functions run on disconnected systems, a student's record may exist in multiple places with conflicting values. A change of address or program in one system does not propagate to others. Generating a consolidated view of a student — attendance, results, fees, and library status — requires manual reconciliation across registers and spreadsheets. This inefficiency motivates a unified platform where every module shares a single source of truth.

1.2 PROBLEM STATEMENT

Existing institution management solutions — including ERPNext Education, openSIS, Fedena, and Moodle-based setups — are either overly heavy and tightly coupled, lack Indian academic workflows, or provide only a learning-management perspective without comprehensive administration, finance, hostel, and transport modules. ERPNext Education is tightly coupled to the broader ERPNext ecosystem, making customisation for Indian academic workflows complex. openSIS is open source but has a dated user interface and limited extensibility. Fedena is a commercial Ruby on Rails school ERP whose licensing restricts deployment for budget-constrained institutions. Moodle-based setups provide a strong learning-management foundation but cover administration, fees, hostel, and transport only weakly when extended beyond course delivery.

None of these offers a hybrid staff interface that combines focused role-specific cockpits with full CRUD access through a rebranded Frappe Desk, together with a student and guardian portal that enforces row-level data scoping at the database level. 2.3 GAP IDENTIFICATION

No existing system combines all of the following: (a) Frappe's metadata-driven agility and DocType data model; (b) Indian academic workflows such as entrance tests, fee structures, schedules, and results publication gating; (c) a hybrid staff interface of role-specific Vue cockpits plus a rebranded Frappe Desk; (d) student and guardian portals with row-level data scoping enforced at the database level through permission_query_conditions; and (e) zero-cost deployment on an open-source stack. This research gap motivates the proposed Institution ERP.

The gap is significant because each missing capability addresses a real administrative pain point. Without metadata-driven agility, adding a new academic entity (for example, a new assessment type or a new fee component) requires schema changes and developer intervention. Without Indian academic workflows, institutions must maintain parallel manual processes for entrance tests and result publication. Without row-level data scoping at the database level, a determined user could bypass UI restrictions and access another student's records through direct API calls. Without zero-cost deployment, many institutions cannot afford the solution at all. Institution ERP closes every one of these gaps.

Institution ERP addresses the identified gaps through a staged build method, a hybrid UI architecture, dual permission mechanisms (User Permissions plus permission_query_conditions), results publication gating, and automated student/guardian creation on admission approval. The design and implementation of these features are detailed in Chapters 4 and 5.

4.11 DESIGN RATIONALE

The hybrid architecture (Option C) was deliberately chosen over two alternatives. Option A — full Vue CRUD — would require reimplementing every DocType form, validation rule, and permission check in Vue, duplicating Frappe's server-side logic at enormous effort and risk. Option B — Desk only — would re-theme Frappe Desk but would not deliver a focused portal experience for staff or a dedicated student/guardian SPA. Option C — the hybrid model — was chosen because it gives staff a fast, role-specific cockpit for the 80% of daily actions (marking attendance, recording payments, publishing notices) while retaining full CRUD through the rebranded Desk for the 20% of operations that need it (creating new records, running reports, bulk imports). This balances usability with completeness without duplicating Frappe's validated forms.

The metadata-driven DocType model was chosen because it allows new entities and fields to be added without code changes, which is essential for an institution whose academic structure evolves each year. The permission_query_conditions layer was chosen because it enforces row-level security at the database level, so security cannot be bypassed by manipulating the UI or calling APIs directly. The results_published flag was chosen because examination marks must be released only after official approval, not the moment an instructor enters them.

5.2 MODULE-BY-MODULE IMPLEMENTATION

5.2.1 Admissions

The admissions pipeline flows Admission Inquiry → Student Applicant → Entrance Test → Entrance Test Result. The Student Applicant DocType implements a four-state workflow (Draft → Applied → Under Review → Approved). On approval, an on_update hook automatically creates a Guardian record (if not existing), a Student record with status Active, and links them — no manual data entry is required after approval.

The Admission Inquiry DocType captures the first point of contact: applicant name, date of birth, gender, guardian details, program interested, source of inquiry, and inquiry date. Each inquiry receives a unique naming series identifier (ADM-INQ-.YYYY.-.####). The inquiry status tracks the conversion funnel from Open to Converted or Closed. This ensures no prospective student is lost and every inquiry can be traced through to enrolment.

The Student Applicant DocType formalises the application. It links to the source inquiry and records the applicant's program, academic year, guardian details, previous school, and previous school marks. The four-state workflow (Draft, Applied, Under Review, Approved) is enforced through Frappe's workflow engine so that an application cannot skip stages. An Entrance Test is optional and tied to a specific program with a date, maximum marks, and passing marks. The Entrance Test Result records marks obtained and auto-calculates Pass/Fail against the test's passing threshold. On approval, the on_update hook creates the Guardian and Student records and sets the created_student reference, completing the conversion from applicant to enrolled student.

5.2.2 SIS (Student Information System)

Student records use naming series STU-.YYYY.-.##### and store first name, last name, status (Active/Inactive/Graduated), gender, date of birth, program, guardian, and email address. Guardian records use format {guardian_name}-{###} and store name, email, phone, and relation. Portal users are created through ensure_student_user() and ensure_guardian_user(), which also create User Permission records for row-level scoping.

The SIS module is the central student registry. Every other module — academics, attendance, examination, fees, library, hostel, transport — references the Student record as the single source of truth. The Guardian record enables family-level access: one guardian can be linked to multiple students, and the portal child-switcher lets a guardian view all linked children from one account. Status tracking (Active, Inactive, Graduated) lets the institution filter current students for reporting without deleting historical records. The unique naming series prevents identifier collisions across academic years.

5.2.3 Academics

Program, Course, Academic Year, Academic Term, Room, Instructor, Student Group, and Course Schedule form the academic hierarchy. Course Schedule prevents double-booking of rooms and instructors on the same day and overlapping time slots. Attendance and assessments are tracked at the student-group level.

The Academics module establishes the organisational structure that every other module depends on. A Program is the degree (for example, B.Sc Computer Science) with a name, code, and department. A Course is a subject within a program with credits and a course type (Core, Elective, Lab). Academic Year and Academic Term define time periods. Room represents a physical space with capacity and type. Instructor links faculty to courses. Student Group is a subset of a program's students for a given year and course. Course Schedule ties course, group, instructor, room, day, and time together, with validation that prevents a room or instructor from being double-booked. This structure ensures that attendance, assessments, and fees all reference a consistent academic calendar.

5.2.4 Attendance

Student Attendance is marked per student group, course schedule, and date, with status Present/Absent/Late/Excused and duplicate prevention per student + date + course schedule. Staff Attendance tracks instructors with Present/Absent/Half Day/On Leave. Bulk marking APIs (mark_bulk_student_attendance, mark_bulk_staff_attendance) skip duplicates.

The Attendance module replaces paper registers. An instructor marks attendance for a student group on a specific date, and each student is marked Present, Absent, Late, or Excused. Duplicate prevention ensures a student cannot be marked twice for the same date and course schedule. Bulk marking lets an instructor mark an entire group at once. Staff attendance follows the same pattern for instructors. The portal shows students their attendance history with colored badges and a percentage calculation, giving students and guardians immediate visibility without visiting the office.

5.2.5 Examination

Grading Scale defines intervals mapping marks to grades with non-overlapping thresholds. Assessment Group carries the results_published flag that gates mark visibility. Assessment Plan links course, student group, grading scale, max marks, and passing marks. Assessment Result supports bulk marks entry, auto grade calculation from the grading scale, auto Pass/Fail status, and duplicate prevention per student per plan. When results_published is 0, portal users see a Results Not Yet Published banner instead of marks.

The results publication gate is a deliberate design decision. In many institutions, instructors enter marks incrementally, and students would see partial or unmoderated results if marks were visible immediately. By gating visibility behind results_published, the examination committee can review all marks for an assessment group, moderate outliers, and release results to all students simultaneously. This ensures fairness and prevents premature disclosure of incomplete results.

5.2.6 Fees

The fee lifecycle is Fee Category → Fee Structure (with components, auto-summed total) → Fee Schedule (with student members) → Fees invoice → Fee Payment → Fee Discount. The Fees DocType recomputes paid and outstanding amounts and status (Paid/Partial/Unpaid/Overdue) on every validate; Fee Payment on submit updates the parent invoice. Fee Discount follows a Pending → Approved → Applied workflow. The Fee Dues Report lists outstanding fees filterable by academic year, program, and status.

The Fees module automates the financial lifecycle. A Fee Structure defines components (tuition, library, lab) for a program and academic year, auto-summing to a total. A Fee Schedule generates the list of students to invoice from a structure, linked to a student group and due date. Each Fees invoice tracks total, discount, paid, and outstanding amounts, with status auto-computed. Fee Payment records each payment and validates it does not exceed outstanding; on submit it recomputes the parent invoice. Fee Discount follows an approval workflow (Pending→Approved→Applied). The Fee Dues Report gives the Fee Manager instant visibility into outstanding collections.

5.2.7 Library

Book Category classifies books. Library Item tracks title, author, ISBN, category, total copies, and available copies (auto-managed). Library Membership specifies max books and validity. Library Transaction records issue/return; issue validates available copies, active membership, and max-book limit; return calculates an overdue fine of ₹5/day, adjusts available copies, and auto-creates a Fees record on late return.

The Library module manages the full issue-return cycle. A student needs an active Library Membership to borrow. On issue, the system validates that copies are available, membership is active, and the student has not exceeded max books. On return, it calculates overdue fines (₹5/day) and, if a fine applies, auto-creates a Fees record so the fine is tracked alongside other fees. Available copies are decremented on issue and incremented on return, keeping the catalog accurate.

5.2.8 Hostel

Hostel stores name, type, warden, and auto-recomputed total capacity from rooms. Hostel Room stores room number, type, capacity, and auto-managed occupied count. Hostel Room Allocation validates that the room is not full and that the student has no other active allocation; it recomputes occupied count on create and vacate.

The Hostel module manages room allocation and occupancy. A Hostel has a total capacity that is recomputed from its rooms. Each Hostel Room has a number, type, capacity, and auto-managed occupied count. Hostel Room Allocation assigns a student to a room, validating that the room is not full and that the student has no other active allocation. Occupied count is updated on create and vacate, giving the Facility Manager real-time occupancy visibility per hostel.

5.2.9 Transport

Vehicle registers number, capacity, driver, and status. Transport Route defines stops (with order and pickup time), vehicle, and fee amount, with no duplicate stop orders. Student Transport Allocation validates vehicle capacity and one active allocation per student per route.

The Transport module manages vehicles, routes, and student allocations. A Vehicle has a number, capacity, driver, and status. A Transport Route has stops with order and pickup time, a vehicle, and a fee amount, with no duplicate stop orders. Student Transport Allocation assigns a student to a route, validating vehicle capacity and one active allocation per student per route. This prevents overbooking and gives the transport coordinator a clear view of route utilisation.

5.2.10 Communication

Notice supports five audience modes (All, Program-wise, Group-wise, Role-wise, Individual) with publish/expiry dates. On publication, the system resolves the audience and creates Notice Recipient records. Communication Log records dispatch (channel, status, sent_at). Feedback supports category, subject, description, and an Open → In Progress → Resolved → Closed lifecycle requiring resolution notes on closure. The Institution Overview Dashboard combines 5 number cards and 2 charts.

The Communication module enables targeted institutional communication. A Notice has a title, body, audience type, and publish/expiry dates. On publication, the system resolves the audience (all students, a program, a group, a role, or an individual) and creates one Notice Recipient record per targeted student, so each student sees only the notices meant for them. Communication Log tracks dispatch channel and status. Feedback lets students and guardians submit complaints with category and subject, tracking them through Open→In Progress→Resolved→Closed with mandatory resolution notes on closure. The Institution Overview Dashboard aggregates 5 number cards and 2 charts for leadership visibility.

5.9 IMPLEMENTATION CHALLENGES AND SOLUTIONS

Several challenges arose during implementation and were resolved as follows. First, Frappe v16 does not auto-sync non-standard Dashboard instances from app JSON, so the Institution Overview Dashboard was created programmatically via frappe.get_doc() in test code and documented in Deployment.md. Second, Frappe v16's Phone fieldtype enforces country-code validation that caused issues with Indian phone numbers, so Vehicle.driver_phone was implemented as a Data fieldtype instead. Third, four Communication module DocType directories lacked __init__.py files; while Frappe v16 does not require them for DocTypes, they were noted as a consistency deviation. Fourth, Guardian naming uses format {guardian_name}-{###}, which can produce similar names for guardians with identical names; this was accepted as a known limitation with a unique-identifier suffix planned for the future. Fifth, the Library fine auto-creates a Fees record without Fee Manager review; this works for the demo but needs an approval workflow for production. Each challenge was documented in ARCHITECTURE.md and DEPLOYMENT.md so future maintainers are aware.

7.7 DISCUSSION

The results confirm that Institution ERP meets its stated objectives. The hybrid staff interface reduces the cognitive load of the full Frappe Desk by presenting role-specific cockpits for daily tasks, while the “Open Full Desk” escape hatch retains access to complete CRUD operations. The results publication gating mechanism addresses a real institutional need: examination marks are released only after official approval, preventing premature disclosure of incomplete or unmoderated results. CHAPTER VIII

CONCLUSION AND FUTURE ENHANCEMENTS

8.1 CONCLUSION

Institution ERP delivers a complete Student Information System on Frappe v16 for Bannari Amman Institute of Technology. The system covers the full student lifecycle — admissions inquiry through graduation — across 10 modules and 48 DocTypes. A hybrid staff interface combines role-specific Vue cockpits with a rebranded Frappe Desk, while Student and Guardian portals provide scoped access through User Permissions and permission_query_conditions. Results publication gating controls mark visibility, and automation handles student/guardian creation, grade calculation, and fee recomputation. All objectives were met: 48 DocTypes, 10 modules, 8 custom roles, 11 whitelisted API methods, 16 row-level permission conditions, 7 end-to-end test suites, and 14 verified demo accounts, deployed at zero infrastructure cost on an open-source stack.

8.2 FUTURE ENHANCEMENTS

The following enhancements are out of scope for this build and are proposed for future work: (1) LMS integration for course content, assignments, and online submission — this would extend Academics beyond scheduling into content delivery and graded coursework; (2) HR/Payroll extending staff attendance into employee profiles, leave management, and salary processing — this would add a human-resources dimension beyond the current staff-attendance scope; (3) payment gateway integration (Razorpay/Stripe) for online fee collection with receipts — this would replace the current manual Fee Payment entry with real-time online collection; (4) real SMS/email gateway replacing the dispatch_notice stub — this would enable actual notice dispatch rather than Communication Log stubs; (5) mobile app consuming the existing REST API — this would expose whitelisted methods and DocType CRUD for native mobile consumption; (6) print format suite for report cards, fee receipts, and ID cards — this would add printable institutional documents; (7) batch/section management for multi-year cohorts — this would add academic batch and section concepts; (8) hostel mess management — this would extend Hostel with meal planning and mess attendance; (9) cockpit customization — this would allow staff to rearrange stat cards and quick actions; and (10) analytics/ML for attendance and fee prediction — this would add predictive insights to the dashboard. None of these are implemented in the current build and are explicitly future scope.

8.3 SUMMARY

Institution ERP demonstrates that a full-featured, role-secured institution management system can be built and deployed at zero infrastructure cost using Frappe v16 and an open-source frontend stack. The system is ready for demonstration and further extension per the future enhancements listed above.
